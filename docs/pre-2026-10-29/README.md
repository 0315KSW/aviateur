## 1. 작업 목적

360도 카메라 프로젝트의 기초 작업으로, 영상 데이터를 압축해 보내고 Windows PC에서 수신·재생하는 경로를 구성했다. 초기에는 AGX Orin의 고해상도 영상 처리와 GStreamer 송수신을 확인했고, 이후 WFB-ng 기반 무선 수신과 Aviateur 수신기 수정으로 진행했다.

수신기 수정의 첫 단계는 성능을 추측하는 대신, 패킷 손실·FEC 복구·디코딩·표시 큐·끊김 복구를 기록할 수 있게 만드는 것이었다. 10월 28일 패치는 계측과 오류 수정이며, 전체 지연이 목표치 이내로 줄었다는 성능 시험 결과는 아니다.

## 2. 진행한 작업

| 단계 | 작업 내용 | 확인 근거와 범위 |
|---|---|---|
| 초기 고해상도 시험 | AGX Orin에서 하드웨어 H.265 인코딩·디코딩 및 GStreamer 영상 송수신 시험 | 앞선 프로젝트 대화에 성공 기록. 실행 명령·원본 로그는 이 저장소에 아직 없음 |
| 무선 송수신 구성 | WFB-ng를 이용해 PC 기반 영상 송수신 구성 | 사용자 설명과 10월 29일 회의의 이전 작업 확인 발언 |
| Windows 수신 | Zadig로 동글의 드라이버를 WinUSB로 교체하고 Aviateur에서 영상 수신 | 사용자 설명. 동글의 정확한 제품·USB ID 및 당시 설정 파일은 별도 보완 필요 |

**성과를 읽는 기준:** 사용자 확인, 소스 구현, 빌드 성공, 실제 장비에서의 성능 측정은 서로 다른 증거다. 코드가 추가됐다는 사실만으로 실제 지연 개선이나 손실 감소가 달성됐다고 적지 않는다.

## 3. 당시 구성

### 3.1 초기 AGX Orin·GStreamer 시험

AGX Orin에서 테스트 영상 또는 저장된 샘플 영상을 처리하고, 압축·전송·수신·재생 기능을 시험했다. 실제 카메라 촬영부터 모니터까지의 지연 검증과는 구분한다.

| 항목 | 대화에 기록된 내용 | 확인 범위 |
|---|---|---|
| 영상 처리 장치 | NVIDIA Jetson AGX Orin | 초기 실험 장비 |
| OS·플랫폼 | Ubuntu 24.04, L4T R39.2.1 | 기존 대화에 기재된 환경. 원본 시스템 출력 보완 필요 |
| 처리 방식 | NVIDIA 하드웨어 인코더·디코더 사용 | NVENC·NVDEC 동작 확인으로 보고됨 |
| 영상 조건 | 7680×3840, 약 30fps | 파일·테스트 영상 처리 결과로 보고됨 |
| 코덱 | H.265 / HEVC | 압축 규격 |
| 송수신 | GStreamer 기반 RTP/UDP | 송수신 성공으로 보고됨 |
| Windows 재생 | GStreamer 1.28.7, `d3d11h265dec` | 초기 GStreamer 수신 경로. Aviateur의 DXVA2 경로와 다름 |

이 표의 결과를 WFB-ng에서 8K 30fps 무선 전송에 성공한 결과로 합치지 않는다. 당시 비트레이트, 전송 경로, 실행 명령과 로그를 연결해서 보완해야 재현할 수 있다.

### 3.2 WFB-ng·Aviateur 수신 시험

| 순서 | 구성 요소 | 역할 |
|---|---|---|
| 1 | 송신 장치·영상 입력 | 영상을 준비하고 압축된 스트림을 송신 경로에 전달 |
| 2 | WFB-ng 송신부·무선 동글 | 영상 패킷에 FEC·암호화 처리를 적용해 무선으로 전달 |
| 3 | 수신 USB 무선 동글 | 무선 데이터를 수신 |
| 4 | WinUSB·libusb·devourer | Windows의 USB 접근 경로와 사용자 공간 동글 제어 |
| 5 | Aviateur의 WFB-ng 수신 코드 | 수신 데이터 복호화·FEC 복구·RTP 출력 |
| 6 | RTP/UDP·SDP·FFmpeg | 압축된 영상 패킷을 해석해 디코더에 전달 |
| 7 | 하드웨어 디코더 | H.265 영상을 디코딩. 사용자 설명의 실제 실행 경로는 DXVA2 |
| 8 | 영상 큐·렌더러 | 디코딩된 프레임을 화면에 표시 |

`lowlat/PATCH1_CHANGES.md`에는 시험 장비로 RTL8812AU와 송신 GX10이 적혀 있다. 정확한 보드·동글 제품명과 실제 운용 역할은 시험 기록과 대조해 보완한다. 관제 PC의 GPU 모델도 자료가 없어 임의로 지정하지 않았다.

## 4. 사용 프로그램과 라이브러리

| 이름 | 무엇인가 | 프로젝트에서 사용한 역할 |
|---|---|---|
| GStreamer | 영상 처리 프레임워크와 명령행 도구 | 초기 영상 생성·압축·패킷화·송수신·재생 시험 |
| `gst-launch-1.0` | GStreamer 요소를 연결해 실행하는 도구 | 파이프라인 시험. 명령행으로 구성해도 개발·검증 작업에 해당 |
| WFB-ng | 무선 패킷 전송 소프트웨어 | 영상 데이터의 무선 전달, FEC, 암호화·복호화 |
| Aviateur v0.3.3 | OpenIPC용 지상 영상 수신·표시 앱 | Windows 수신기 기반 프로그램 |
| Zadig | Windows USB 장치의 드라이버 교체 도구 | 대상 동글에 WinUSB 적용 |
| WinUSB | Windows USB 장치 접근용 드라이버 | 앱이 대상 USB 장치에 접근할 수 있게 함 |
| libusb | USB 접근 라이브러리 | Aviateur·devourer와 Windows USB 접근 연결 |
| devourer | 사용자 공간 무선 동글 드라이버 | 앱에서 동글 제어·수신 처리 |
| FFmpeg / libav* | 미디어 입력·해석·코덱 라이브러리 | RTP/SDP 해석과 영상 디코딩 |
| DXVA2 | Windows 하드웨어 영상 가속 인터페이스 | 사용자 설명상 H.265 하드웨어 디코딩 경로 |
| libsodium | 암호화 라이브러리 | WFB-ng 암호화·복호화 관련 의존성 |
| SDL3·vecgui | 화면·오디오·GUI 관련 라이브러리 | Aviateur의 재생·사용자 인터페이스 기반 |
| CMake·MSVC·vcpkg | 빌드 구성·컴파일러·의존성 관리 | Windows 수정본 빌드 |
| Git·GitHub Actions | 소스 이력·자동 빌드 | 수정 내용 관리와 실행 패키지 생성 |

H.265는 프로그램 이름이 아니라 압축 규격이다. RTP는 미디어 패킷 형식, UDP는 전송 방식이다. FEC는 일부 손실을 복구하도록 추가 데이터를 보내는 방식이다. URB는 USB 전송 요청이며 영상 프레임 수와 같지 않다.

## 5. 원본 프로그램과 직접 수정한 부분

### 원본에서 사용한 기능

- 무선 동글 제어, WFB-ng 복호화·FEC 처리.
- RTP/UDP 전달과 SDP 입력, FFmpeg 디코딩.
- 하드웨어 디코더 탐색·선택, 프레임 큐와 화면 표시.
- 장치·키·채널 설정 화면.

### 10월 28일 추가·수정한 기능

1. Windows에서 바이너리 키가 잘못 읽히는 문제 수정.
2. USB 수신 요청 수 등 환경변수를 읽어 devourer 설정으로 전달.
3. RTP 번호가 65535에서 0으로 순환할 때 누락 계산 오류 수정.
4. 패킷·FEC·디코딩·표시 큐 통계를 CSV와 로그에 저장.
5. 끊김·재수신·프레임 인출 이벤트와 시간을 기록.
6. 로그 콜백에 빈 문자열이 전달되던 문제 수정.
7. 큐 설정 비교용 실행 배치 파일과 Windows 자동 빌드 추가.

상세 코드는 [CODE_CHANGES.md](CODE_CHANGES.md)에 정리했다. zero-copy 렌더링, 내부 UDP 제거, 디코더 재연결 대기 단축, intra-refresh 도입은 이 패치의 완료 항목이 아니다.

## 7. 현재 결과와 한계

- Windows 수정본 자동 빌드 성공 2건과 다운로드용 아티팩트 생성을 확인했다.
- 영상 수신 성공과 수정본의 성능 개선 성공은 구분한다. 이 문서에 첨부된 실제 장비 CSV·영상·송신 로그는 없다.
- DXVA2 사용은 사용자 설명을 반영했다. 소스가 DXVA2 하나로 고정돼 있는 것은 아니며 실제 선택값은 실행 로그로 확인해야 한다.
- 4K 30fps, 720p 120fps는 회의 초반의 이전 시험 설명에 나온다. 해상도별 비트레이트·손실·지연 조건이 함께 기록되지 않아 동일 시험으로 합치지 않는다.
- 회의의 300~400ms 관찰값을 정밀 측정 결과로 사용하지 않는다.
- 업체가 설명한 300m·600m 거리, 라파 수신기에서 LAN으로 PC에 전달한 결과는 이 수신기 패치의 개인 성과로 포함하지 않는다.

## 8. 10월 29일 이후 요청과의 경계

실제 카메라 연결, 별도 송수신 게이트웨이, 뒷단 장비 양방향 접근, 전체 150ms 목표, 자동 실행은 후속 회의에서 구체화된 요청이다. 이 문서는 그 계획을 10월 28일까지의 완료 실적으로 포함하지 않는다.

다음 기록 보완은 [시험 결과 문서](TEST_RESULTS.md)의 미확인 항목을 채우는 방식으로 진행한다. 송신 원본 명령과 실행 로그가 확보되면 기존 구성의 재현 절차를 완성할 수 있다.
