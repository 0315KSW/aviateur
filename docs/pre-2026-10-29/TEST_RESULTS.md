## 2. Windows 빌드 증거

| 구분 | 소스 | 실행 | KST 시작 → 종료 | 결론 |
|---|---|---|---|---|
| 패치 1 | `0d1ab0d` | [40642333803](https://github.com/0315KSW/aviateur/actions/runs/40642333803) | 10/28 15:11:13 → 15:40:25 | success |
| 패치 1.1 | `15f511c` | [40653795188](https://github.com/0315KSW/aviateur/actions/runs/40653795188) | 10/28 17:00:51 → 17:38:04 | success |

패키지명: `Aviateur_lowlat_windows_x86_64`.

빌드 성공은 소스가 해당 CI 환경에서 컴파일·패키징됐다는 증거다. 실제 동글에서의 수신 성공, 하드웨어 디코딩 성공, 지연 목표 달성은 별도 실행 기록이 필요하다.

기존 `PATCH1_CHANGES.md`에는 Linux 빌드와 통계 단위 시험 성공도 기술돼 있다. 이 보고서에서는 그 실행 로그를 별도로 확보하지 못했으므로 Windows CI처럼 직접 확인한 결과로 격상하지 않았다.

| 전체 150ms 이내 | 후속 개발 목표 | 10월 28일까지의 달성 실적 |

## 4. 기존 패치 통계를 읽을 때의 주의

- 송신 패킷 수와 수신 `video_frames`를 비교하려면 같은 세션·채널·측정 단위를 맞춰야 한다. FEC 패킷·세션 패킷·다중 안테나 중복을 구분하지 않으면 단순 차이를 손실률로 사용할 수 없다.
- `fec_recovered`는 복구한 패킷 수다. 원인이 전파인지 USB 처리인지 이 값만으로 구분하지 못한다.
- `lost_after_fec=0`이어도 송신 입력의 손상, 이전 오류의 영향, 헤더 문제, 디코딩·표시 문제 등을 추가로 확인해야 한다.
- `queue_wait_*`는 전체 지연이 아니라 디코딩 후 큐 대기 부분이다.
- `recovery`는 영상 채널 패킷 재수신 뒤 프레임을 큐에서 꺼낼 때까지의 진단값이다. 정상 화면 복구·실제 표시 완료·새 프레임임을 보장하지 않는다.
- 로그 저장 자체도 부하를 만들 수 있으므로 향후 성능 비교는 같은 계측 조건에서 수행한다.

## 5. 실제 시험 기록을 보완할 표

아래 표는 새 실적이 아니라 아직 확보하지 못한 기록의 목록이다.

| 항목 | 현재 상태 |
|---|---|
| 송신 장치·OS·정확한 역할 | 기존 패치 문서에 GX10 언급. 모델·역할 확인 필요 |
| 수신 PC·GPU·드라이버 버전 | 사용자 설명은 Windows·DXVA2. 시스템 정보·로그 필요 |
| 송수신 동글 모델·칩셋·USB ID | 기존 문서에 RTL8812AU. 실제 장치 정보 필요 |
| 영상 입력·원본 영상 | 파일명·해상도·FPS·코덱·길이 필요 |
| 송신 비트레이트와 실제 출력 FPS | 원본 명령·계측 로그 필요 |
| WFB 채널·폭·MCS·FEC·출력 | 원본 설정 필요. 기존 A/B 안내의 36·20MHz·MCS1은 안내 조건이지 실제 실행 증거가 아님 |
| 실제 사용한 키·포트·link ID 설정 방법 | 키 내용 제외, 설정 파일·명령 필요 |
| 원본·수정본 수신 앱 버전 | 수정 소스는 `15f511c`. 현장 실행 파일은 `BUILD_COMMIT.txt`·로그로 연결 필요 |
| 8·16·32 비교 로그 | 각 회차 console·app log·CSV 필요 |
| 전체 영상 지연 | 같은 조건으로 원본 장면과 수신 화면을 비교한 영상·측정표 필요 |
| 끊김 복구 | 단절 조건·재수신 시각·정상 새 영상 표시 시점 필요 |

## 6. 미확인 항목을 채우는 순서

1. 당시 송신 명령·설정과 실행한 수신 패키지의 커밋을 확보한다.
2. 이미 존재하는 시험 로그가 있으면 원본 그대로 보관하고 조건을 연결한다.
3. 실행 이력이 없는 항목은 빈칸을 유지하고 새로 시험한 날짜를 따로 기록한다.
4. 후속 시험 결과를 10월 28일까지의 실적으로 소급해서 적지 않는다.
