# 09. 10/29 회의와 다음 단계

근거: 10/29 회의 녹음(녹음본 1·2, 뉴딕스 2일차 녹음 3개)과 손글씨 메모. 회의 발언을 옮긴 것이며 확정 사양은 아닙니다.

## 회의에서 바뀐 것

### 목표 구조
```
영상
카메라 ─유선 LAN─▶ 송신 장치(WFB-ng) ~~무선~~▶ 수신 장치(WFB-ng, 게이트웨이) ─유선 LAN/허브─▶ PC(표시·제어)

제어·응답 (반대 방향)
PC ◀──▶ 수신 장치 ◀~~무선~~▶ 송신 장치 ◀──▶ 카메라·드론
```

| 항목 | 10/22 기준 | 10/29 회의 |
|---|---|---|
| 구조 | PC 두 대 사이 무선 전송 | 카메라와 PC 사이에 송신 장치·수신 게이트웨이를 따로 둠 |
| 방향 | 영상 한 방향 | 영상 + 반대 방향 제어·요청·응답 (시리얼·이더넷 데이터, 드론 제어 프로토콜, SSH) |
| 지연 목표 | 200~300ms 이하 | **전체 경로 약 150ms 이내** |
| 송신 장치 | GX10 | 실제 제품은 작은 상용 보드 구상. 보드의 카메라보다 LAN 입력과 통신 기능이 중요 |
| 수신 장치 | PC가 직접 수신·표시 | 수신 장치는 게이트웨이·라우터 역할, 표시는 별도 PC |

### 회의에서 나온 수치 (발언, 실측 아님)
- 현재 화면 지연 약 0.3초(300~400ms). 무선 구간 자체는 최대 약 50ms로 봄.
- 줄여야 할 부분은 카메라·USB 입력과 영상 처리 쪽이라는 설명.

### 요청 사항
1. 지금까지 한 코드와 설치·설정 과정을 Git에 정리 (→ 이 저장소)
2. 라즈베리파이와 직접 연결한 카메라로 영상 입력·전송 확인 (USB 입력 장치와 비교해 지연 원인 분리)
3. 송신부의 LAN 입력, 수신부에서 별도 PC로 전달하는 구성
4. 원격 장비 뒤쪽까지 제어·요청·응답이 통하도록 터널링·라우팅·포트 포워딩 검토
5. 전체 지연을 재고 USB 입력·인코딩·전송·표시 중 어디서 생기는지 나누기
6. 전원을 다시 켰을 때 설정이 적용되도록 서비스 자동 시작과 문서화
7. 채널·안테나·출력에 따른 거리와 끊김 비교

10.50.0.x 주소와 SSH 포트 변경 예시가 나왔지만 완성된 네트워크 설정표는 아닙니다. 구체적 IP·포트는 확정하지 않았습니다.

## 라즈베리파이 4로 할 수 있는 것 (공식 사양 기준)

| 기능 | 라즈베리파이 4 |
|---|---|
| 하드웨어 인코딩 | H.264, 1080p30까지 |
| 하드웨어 디코딩 | H.265 4Kp60까지 |
| HDMI 출력 | 4Kp60 |
| H.265 하드웨어 인코딩 | 없음 |

- **카메라 쪽으로 쓰면:** 4K 하드웨어 인코딩이 안 되므로 1080p30 H.264가 현실적인 상한입니다. 지연 원인 분리 시험에는 충분합니다.
- **수신 게이트웨이로 쓰면:** 영상은 디코딩하지 않고 전달만 하므로 코덱 제약이 없습니다. 리눅스 드라이버(`88XXau_wfb`)를 쓰므로 Windows 사용자 공간 드라이버와 손실을 비교할 수 있습니다.
- 회의에서 라즈베리파이 5는 하드웨어 인코더가 없어 피하자는 발언이 있었습니다.

## 다음 단계 계획 (제안, 업체와 확정 전)

### 시험 구조 제안
```
[Pi4 #1 카메라 노드] ─LAN─▶ [송신: GX10 또는 소형 보드, WFB-ng] ~~5GHz~~▶ [Pi4 #2 수신 게이트웨이, WFB-ng] ─LAN─▶ [Windows PC 디코딩·표시]
        H.264 1080p30                                                   리눅스 드라이버, 터널                       Aviateur 또는 FFmpeg
```

| 구간 | 주소 대역 (제안) |
|---|---|
| 송신 쪽 LAN (카메라 ↔ 송신 장치) | 192.168.10.0/24 |
| WFB-ng 터널 (송신 ↔ 수신) | 10.50.0.0/24 |
| 지상 LAN (게이트웨이 ↔ PC) | 192.168.20.0/24 |

- 영상: UDP/RTP로 게이트웨이까지 오면 게이트웨이가 PC로 전달. 프레임 조립·디코딩은 PC에서.
- 제어: WFB-ng 내장 IP 터널로 양쪽 LAN 사이 라우팅 또는 포트 포워딩.
- 부팅 시 자동 시작: 송신·게이트웨이의 WFB-ng와 전달 설정을 systemd 서비스로.

### 계속할 일
- 4K 손실 원인 분리: 수신 PC 실행 파일을 패치 1.1로 바꾸고 `run_urbs8.bat`/`run_urbs16.bat`/`run_urbs32.bat` 비교, 리눅스 게이트웨이 수신과 비교.
- 종단 지연 측정: 초시계를 원본과 수신 화면에 함께 촬영.
- 비트레이트 단계 상향: 40MHz·높은 MCS로 무선 용량을 늘리며 3 → 8 → 15 → 20~25Mbps.
- 송신 쪽 `tx/` 폴더에 스크립트·설정 추가 (송신 담당).
