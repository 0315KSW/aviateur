# 06. 시험 결과 (10/27~10/28)

모든 수치는 `tools/`의 스크립트로 `data/`의 원본을 집계한 값입니다. 다시 확인하려면:
```
python3 tools/analyze_aviateur_log.py data/receiver_logs/<파일>
python3 tools/analyze_link_csv.py data/receiver_csv/link_20261028_163234.csv [--window HH:MM:SS-HH:MM:SS]
```

송신 쪽 수치(주입 패킷, fps, 비트레이트)는 송신 측 최종 보고 값입니다.

공통 조건: 채널 36·20MHz, MCS 1, FEC 8/12 (13:3x 로그의 `SESSION 0:1:8:12`로 확인).

"수신/주입"은 같은 60초에 송신이 주입했다고 기록한 패킷 수 대비 수신이 받은 영상 채널 프레임 수의 비율입니다(참고값).

### 이 데이터로 말할 수 있는 것
- **같은 파일, 같은 설정인데 회차마다 손실이 크게 달랐습니다.** 1회차는 60초 동안 FEC 후 손실 0으로 깨끗했습니다.
- 송신 쪽 WFB-ng는 세 구간 모두 주입을 꾸준히 했고 드롭이 0이었습니다. 그런데 수신 쪽 받은 패킷 수가 회차마다 달랐습니다.
- 따라서 손실은 **GX10의 WFB-ng 이후 구간**(송신 동글 → 전파 → 수신 동글 → USB → 드라이버)에서 생깁니다. 인코더나 송신 프로그램 문제는 아닙니다.
- 회차별 SNR이 손실과 함께 움직였습니다(손실이 적은 1회차 33.7dB, 많은 2회차 27.3dB). 무선 상태가 회차마다 달랐을 가능성이 있습니다.

### 아직 말할 수 없는 것
- 손실이 전파 구간인지, 수신 동글·USB·사용자 공간 드라이버인지는 이 데이터만으로 나눌 수 없습니다. 패킷이 동글에서 버려지면 수신 쪽에서는 "안 들어온 것"으로만 보입니다.
- 무엇이 회차마다 SNR을 바꿨는지(사람·물체 이동, 안테나 방향, 간섭 등)는 기록이 없습니다.
- 송신 "주입" 수는 송신 동글이 실제로 전파를 내보낸 수를 보증하지 않습니다.

## 4. 측정하지 못한 것
- **종단 지연(카메라 → 화면)**: 아직 측정하지 않았습니다. 손실을 먼저 안정시킨 뒤 회의에서 정한 방법(초시계를 원본과 수신 화면에 함께 찍기)으로 잴 계획입니다.
- 20~25Mbps 전송: 현재 무선 설정(MCS 1·20MHz)으로는 용량이 부족해 시험하지 않았습니다.
- 거리 시험: 실내 근거리에서만 시험했습니다.
- 끊김 후 복구 시간: 패치 1에 측정 기능을 넣었지만 아직 의도적인 끊김 시험은 하지 않았습니다.
