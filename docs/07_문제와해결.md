## 판단을 고친 것 (기록)

진행 중 잘못 판단했다가 데이터로 바로잡은 내용입니다. 같은 실수를 반복하지 않기 위해 남깁니다.

| 처음 판단 | 데이터 확인 후 |
|---|---|
| "SNR이 안정적이라 신호 세기는 원인이 아니다" | 회차별로 보면 SNR이 손실과 함께 움직임(33.7dB vs 27.3dB). 무선 상태를 원인에서 뺄 수 없음 |
| "송신 쪽 데이터가 시간이 지나며 줄었다" | 송신 주입은 세 구간 모두 일정(17,098 / 18,977 / 18,999), 드롭 0 |
| 10/28 720p를 시험 패턴으로 봄 | Femto 실시간 영상 약 1.5Mbps |
| "송신 드롭은 원인에서 제외" | 제외할 수 있는 것은 GX10의 WFB-ng 단계 드롭뿐. 송신 동글 단계는 제외 못 함 |
| 16:32 세 회차를 USB 큐 8/16/32 비교로 기록 (외부 보고서) | 세 회차 모두 큐 8, Aviateur 한 번 실행, 콘솔 로그 없음. 큐 비교 시험은 아직 안 함 |
| 11/3 ch48 한 번 결과로 "ch36 간섭이 원인"이라고 봄 | 송신 지적: 시간에 따른 변화일 수 있으니 ch36으로 되돌려 재야 함 → 20:11 ch36 6.1%, 20:15 ch48 0.77%로 확인 |
| 11/3 `fec_rec`까지 손실처럼 봄 (송신 지적) | 화면 깨짐은 `lost`로 판단. `fec_rec`는 FEC가 살린 것 |
| 11/3 "출력 부족이 원인" | 인덱스 1 → 10(+6dB)에서 효과 없음 |
| 11/5 18:36 녹화를 5610 직접 경로로 봄 | `agx_test.bat`로 띄운 5600(무선) 경로였음 |
| 11/6 "남은 지연은 카메라 처리" | 카메라 Pi가 Wi-Fi로 보내고 있었음. 절전 끔으로 약 90ms 감소 |
| 11/6 "무선 구간은 20ms" | 같은 녹화 두 창의 차이를 본 관찰값. Pi Wi-Fi가 낀 조건이라 WFB 구간 확정치 아님 |
